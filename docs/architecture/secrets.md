# Secrets: what exists, who holds it, and what changing it costs

`17-03`, 2026-08-27. **This file names secrets and says where they live. It never contains one, and
neither does any repository in this project** (`repositories.md`, "No secrets, ever"). If a value ever
appears here, that is the bug.

The rotation procedures are in `docs/runbooks/secret-rotation.md`, together with the leak procedure.
This file answers "what is there"; the runbook answers "how do I change it and what breaks while I
do".

## How this list was built, so a reader can check it rather than trust it

Six sweeps, because "short and factual" is easy and "complete" is the part worth anything. Anyone
re-running these should find the same set.

**All six were last re-run on 2026-09-06 (`24-14`)**, and they did not find the same set: one missing
key, a PAT in three repositories where this file said two, and a repository recorded as having no
workflow that has one. Sweeps 1, 2, 3 and 5 are now `tools/secrets-audit.sh`, which exits non-zero on
anything it finds that this file does not name. Sweeps 4 and 6 stay manual, deliberately — one needs a
human to say whether a string is a secret or a fixture, the other reads prose — so a re-run of *those*
two is still a person's job, and the date above is when that was last done.


1. **Every key in the three `secretGenerator` sources** — `ago-deploy/docker/.env.example`,
   `k8s/overlays/local/.env.example`, `k8s/overlays/demo/.env.example`.
2. **Every `$(VAR)` substitution in `ago-deploy/k8s/`** — this is the sweep that catches a variable a
   manifest *consumes* but no `.env.example` documents, and it found one (see the note under
   `KEYCLOAK_DEMO_PROVISIONER_SECRET`).
3. **Every `secretKeyRef` in `ago-deploy/k8s/`.**
4. **Every credential-shaped literal committed in a manifest or an `appsettings*.json`** — the sweep
   that finds a secret whose value is *not* in a Secret at all. It found one, and it is the open
   finding at the bottom of this file.
5. **Every `secrets.*` reference in every repository's `.github/workflows/`** — **all ten
   repositories**, including the two that have no workflow at all. This said *seven* until
   `24-14` re-ran it: `ago-faq` was never swept at all, and `ago-landing` was swept once, recorded
   as having no workflow, and has had one since. A sweep whose own scope is a number written down
   once is a sweep that stops covering the thing it was defined over — which is why
   `tools/secrets-audit.sh` enumerates the workspace rather than carrying a list.
6. **Every credential named in an ADR or runbook but held outside every repository** — the node's own
   keys, the backup keypair, and anything a human keeps on a laptop. `adr/0050` explicitly assigns its
   key to this inventory; the rest come from `public-deploy.md`, `backup-and-restore.md` and
   `adr/0040`.

**Sweeps 1, 2 and 3 also produce names that are not secrets** — a role name, a username, an SMTP
host, a port. Those are not listed below, and a reader re-running the sweeps will therefore find
about sixteen names this file does not mention and should not. `tools/secrets-audit.sh` carries the
exclusions explicitly, each with its reason, so "the same set" is checkable rather than a matter of
agreeing about what counts.

What the sweeps deliberately do **not** cover: git history. Auditing history for previously committed
secrets is a different technique and `17-03` puts it out of scope; nothing in these sweeps suggested a
reason to bring it forward.

## The rotation-cost classes

Every entry below is labelled with one of four. The classes exist because "rotate your secrets
regularly" is advice that ignores the only question that decides whether anyone ever does.

| Class | What a rotation costs | Who notices |
|---|---|---|
| **Restart** | Change the value, redeploy. The process reconnects. | Nobody, beyond the rollout itself |
| **Coordinated** | Two or more places must change, and the order matters | Nobody if the order is right; a broken component if it is not |
| **Draining** | Old and new are both valid for a stated window, then the old one expires | Nobody, provided the window is respected |
| **Breaking** | Something in use stops working the moment the value changes | A user, immediately |

Before `17-03` the visitor signing key was **Breaking**, which is exactly why it had never been
rotated. `adr/0067` moved it to **Draining**. That single reclassification is the item.

## A. The deployment's own credentials — the `infra-credentials` Secret

machine doing the deploy. The repository carries `.env.example` files that document shape and never
values. `git check-ignore` confirms the bare `.env` pattern covers them, and `git ls-files` finds no
tracked `.env` anywhere.

Notes that change what a reader would otherwise assume:

- **The internal CA's key is the one row in this table whose rotation reaches outside the cluster
  entirely.** Every other `Coordinated` row here is two or more *deployment-side* places changing
  together. This one is not: the public half is committed source in **two repositories**, and one of
  them (`ago-chat`) only takes effect once its image is rebuilt and republished — so "rotate the
  credential" is, for this one row, "cut a change, get it through CI, redeploy" before the Secret edit
  even matters. Until that image ships, `ago-calendar-api`'s new leaf (signed by whatever key
  `ago-internal-ca` now holds) is presented to a chat pod still trusting the old root, and the module
  channel fails closed (`ModuleUnreachableException`) rather than silently. There is no faster path,
  and `adr/0137` sized the root's own validity (10 years) specifically so this sequence is rare.

- **`KEYCLOAK_ADMIN_PASSWORD` stopped being a deployment setting at `15-01`/`adr/0036`.** Keycloak now
  has a database that remembers the admin account, so this value is first-boot-only: editing it and
  re-applying changes the Secret and not the account. Rotating the actual admin password is a realm
  operation (`runbooks/realm-operations.md`), and the entry is here rather than omitted precisely
  because the obvious edit does nothing.
- **`KEYCLOAK_DEMO_PROVISIONER_SECRET` is consumed by `k8s/base/api.yaml` and `worker.yaml` but was
  documented in neither `.env.example`** until this item added it. It is the one thing sweep 2 found
  that sweep 1 did not, and the consequence was real: a node rebuilt from `.env.example` would come up
  with the demo-tenant endpoint enabled and a placeholder for its credential.
- **`KEYCLOAK_SMTP_PASSWORD` is empty by decision, not by omission** (`adr/0040`'s amendment). Mail
  goes to the node's own Postfix across the cluster bridge, which takes no SMTP AUTH and no TLS,
  because the hop never leaves the machine. There is no credential to hold.
- **`AUTH_JWT_SIGNING_KEY` is one key shared by every site.** It is the whole subject of `adr/0067`;
  what it grants is the binding to one existing conversation's history, and nothing else, because the
  minting endpoint is public and unauthenticated by design (`adr/0034`).
- **`CHANNELS_CREDENTIAL_ENCRYPTION_KEY` is the same rotation shape as the open finding at the
  bottom of this file, and the opposite storage shape.** Reversible encryption over stored
  ciphertext: changing the value without re-encrypting does not fail loudly, it silently makes every
  already-registered channel credential undecryptable, so a tenant's Telegram bot stops delivering
  and nothing says why. That is what puts it in **Breaking** rather than Restart, and it is the fact
  a reader consults this file to learn. Where it differs from `Webhooks:SecretEncryptionKey` is that
  it was **sourced from `infra-credentials` from day one** — `k8s/base/api.yaml`'s own comment beside
  it says so, in as many words, citing the finding on the line above it as the thing not to repeat.
  It was missing from this inventory, not from the Secret.
- **This entry is why `tools/secrets-audit.sh` exists.** `17-03` wrote this file on 2026-08-27 and
  `14-01`'s channel storage landed within days; nothing then made adding a secret update the
  inventory, and ten days later the file was missing a key, understating a PAT's blast radius by a
  third, and asserting a repository had no workflow when it had one. `personal-data.md` stays true
  because three separate places make adding a column update it. This file now has one place, and it
  is mechanical.
- **There is one Postgres role, not two, and `adr/0056` assigned that observation here.** With DDL
  confined to `Ago.Chat.Migrator`, the three serving hosts could run under a DML-only role — a genuine
  reduction, since an application compromise then could not alter the schema. It needs two roles, two
  connection strings and the grants to go with them, and it is **not done**. It is recorded here rather
  than done here because it is a privilege change, not a rotation: `17-03`'s subject is what happens
  when a credential's *value* changes, and adding a credential is a different item. Naming it keeps the
  count of Postgres credentials in this inventory honest at one.

## B. Secrets whose value is in the repository

Two, and they are opposite cases: one is a deliberate published value, the other is an open finding.

| Name | Where | Status |
|---|---|---|
| The three seeded Keycloak demo accounts' passwords | `ago-deploy/k8s/base/keycloak-realm-import.json` | **Published by decision** (`adr/0034`) |
| `Webhooks:SecretEncryptionKey` | `ago-deploy/k8s/base/{api,worker,webhooks}.yaml`, and three `appsettings.Development.json` in `ago-chat` | **Open finding — see the last section** |

**`Channels:CredentialEncryptionKey` also has a committed literal, in the same three
`appsettings.Development.json` files, and it is deliberately not listed above.** Sweep 4 finds it and
a reader re-running that sweep will too, so it is worth saying why it is not a third row: a
`Development` value is overridden by the environment everywhere that is not a developer's own
machine, and every manifest that serves a real deployment supplies this one from `infra-credentials`.
What makes the webhook key a finding is not that a literal exists — it is that `base/*.yaml` sets it
as a literal and the demo overlay does not override it, so the committed value is the one actually
protecting live data. The two cases look identical to a grep and are not the same fact.

The seeded demo passwords are published on purpose: `adr/0034` reasons about this realm on the basis
that every account in it is a demo account whose password is in a public repository, and that is what
makes mandatory TOTP ceremony rather than protection there. The trigger it names for revisiting is the
first account in the realm that is not a demo account. Note also that since `15-01` the realm import
only seeds on first boot, so whether those passwords still hold on the live deployment is live state,
changed through `runbooks/realm-operations.md` rather than by editing that file.

## C. CI

| Name | Where | Scope | Expires | Class |
|---|---|---|---|---|
| `AGO_PLATFORM_PACKAGES_TOKEN` | Repository secret in **three** repositories: `ago-chat`, `ago-calendar` and `ago-faq` | Classic PAT, `read:packages` only | **2027-08-25** | Coordinated |
| `GITHUB_TOKEN` | Not held anywhere — GitHub mints it per job | Per-workflow `permissions:` block | Per job | n/a |

Sweep 5 in full, re-run 2026-09-06 over all ten repositories: `ago-chat`, `ago-calendar` **and
`ago-faq`** reference `secrets.AGO_PLATFORM_PACKAGES_TOKEN`; `ago-chat`, `ago-console`,
`ago-widget`, `ago-calendar-console` **and `ago-landing`** reference `secrets.GITHUB_TOKEN` for a
GHCR login; `ago-platform` uses `GITHUB_TOKEN` to push packages; `ago-deploy` and `ago-root`
reference no secret at all, and have no workflow.

Three facts worth keeping beside the PAT:

- **One value in three repositories is deliberate; the *third* copy was not recorded.** A personal
  account has no shared Actions secret, so the copies are unavoidable. What was avoidable is the
  inventory saying two: `ago-faq` restores `Ago.Platform.*` in CI exactly as the other two do, and
  its most recent commit is literally `chore: retrigger CI after re-setting
  AGO_PLATFORM_PACKAGES_TOKEN`. Somebody had already paid the cost of a third copy while this file
  said there were two — so the drift was not hypothetical, and the number that was wrong is the one
  a rotation is planned against.
- **The expiry now fires.** `ago-chat/.github/workflows/credential-expiry.yml` is a scheduled workflow
  that fails when the date is inside 30 days, because a date written in a backlog file is a record and
  not a reminder. Its own limitation is in its header and repeated in the runbook: GitHub disables
  scheduled workflows in a repository with no activity for 60 days.
- **`ago-platform` holds no secret at all** — it *publishes* with `permissions: packages: write` and
  the built-in `GITHUB_TOKEN`. That is direct evidence the consuming side could plausibly do the same:
  `adr/0018` justified the PAT by noting GitHub forbids *anonymous* reads, which is true and does not
  describe `GITHUB_TOKEN`. Granting each package Actions-read access to the consuming repository would
  remove this credential from this inventory rather than rotating it forever. Untested, and the
  cheapest experiment on this page.

## E. Credentials held outside every repository and outside the cluster

The ones a checked-in inventory most easily misses, because nothing in a repository points at them.

| Name | Where | Protects | Class |
|---|---|---|---|
| The node's SSH private key | The author's machine, `~/.ssh/ago-vps-ed25519` | The whole deployment. Password authentication and root login are off (`17-05`), so this key is the only way in | Breaking-if-lost |
| The backup GPG private key **and its passphrase** | The author's machine, `~/.ago-backup/gnupg` — never on the node | Every backup artifact ever taken | See below |
| The backup recipient *public* key | On the node | Nothing. Not a secret; listed so its counterpart is not mistaken for one | Restart |
| The OpenDKIM signing key | The node, selector `mail` | The authenticity of outbound mail from the sending domain | Coordinated (key and DNS record must change together) |
| The `ago` node account and its sudo rights | The node | Everything on it | Breaking-if-lost |

**The backup key's cost is stated in `adr/0050` and repeated here because it is the sharpest one in
this file: lose that private key and every artifact ever taken is permanently unreadable.** There is no
escrow and no recovery. Rotating it does not re-encrypt existing artifacts, so a rotation splits the
archive at a date and both keys must be kept for as long as the older half is wanted. The runbook says
so where the procedure is.

## F. Secrets this system generates for its tenants

| Name | Where | Rotation |
|---|---|---|
| A webhook endpoint's signing secret | Generated per endpoint, shown once at registration, stored **encrypted** in `webhook_endpoints` (`adr/0024`) | The tenant re-registers the endpoint. AGO cannot show an existing one again |
| A visitor session token | `localStorage` in the visitor's own browser | Renews at the point of use (`adr/0048`); seven-day lifetime; no revocation, by decision (`adr/0034`) |

A site's **public key** is not on this list and is not a secret — it is embedded in the `<script>` tag
on a shop's public page by construction (`adr/0029`).

## Open finding: the webhook secret-encryption key is a committed value

**`Webhooks:SecretEncryptionKey` is an AES-256 key that encrypts every tenant's webhook signing secret
at rest, and its value is committed in this project's public repositories.** It reaches the demo
deployment through `ago-deploy/k8s/base/{api,worker,webhooks}.yaml`, which set it as a literal rather
than from `infra-credentials`, and the demo overlay does not override it.

Stated specifically rather than vaguely, per `repositories.md`'s rule for an open finding: this is
derivable by opening the manifest, so describing it obliquely would buy nothing and cost the reasoning.

- **What it is worth to an attacker**: it decrypts `webhook_endpoints.secret` — but only for someone
  who already has the database rows or a backup artifact. It is not a remote credential; it is the
  second half of one. With both, they could forge a signature that a tenant's endpoint would accept as
  genuinely from AGO.
- **How it got there**: `7-03` added it to the manifests to stop a crash-loop, copying the pattern from
  `appsettings.Development.json` and describing it as "the same throwaway local dev value". That was
  true of the local loop and became untrue when `base/` started serving the public deployment.
  `WebhookSecretCipherOptions`' own doc comment still says the key is bound "from the same
  `infra-credentials` mechanism `Auth:SigningKey` already uses", which is what the manifests should
  have done and is not what they do.
- **Why this item did not simply fix it**: `adr/0024` chose reversible encryption precisely so a
  secret can be shown to a tenant again — which means the stored ciphertext is load-bearing. Changing
  the key without re-encrypting makes every already-registered webhook secret permanently
  unrecoverable, silently, exactly as `WebhookSecretCipherOptions` warns. There is no re-encryption
  path in this system, so the fix is an item with a migration in it and not a manifest edit. `17-03`
  builds the mechanism for one key and inventories the rest; this is the "something the present
  approach genuinely cannot hold" its own Out-of-scope section says becomes its own item.
- **What the fix looks like**: a second key setting (current + previous), decrypt-with-either,
  re-encrypt-on-read or a one-shot re-encryption job, then move the value into `infra-credentials`
  where its neighbours already are. Structurally the same shape `adr/0067` just built for the signing
  key, applied to data at rest instead of tokens in flight.

Until that item exists and lands, `runbooks/secret-rotation.md` carries the honest interim procedure,
which is "revoke and re-register", and says what it costs.
