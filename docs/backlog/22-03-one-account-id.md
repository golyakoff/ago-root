# One account id — the calendar's tenancy equals it, rather than being replaced by it

- **Stage**: 22
- **Status**: done (2026-09-03), `ago-calendar#29`
- **Depends on**: `22-01`

## What changes

AGO Calendar stops minting its own tenancy. Its tenant id becomes the account id — the same value
`ago-chat` already calls `SiteId` and `ago-faq` already uses directly as its own scope key (`19-03`).

**The wording carries the whole decision.** *Equals*, not *replaced by*:

- The calendar **keeps its `tenants` table.** Nine tables hold a foreign key to it, and the granted
  worker quota (`22-07`) has to be readable inside a calendar transaction, which rule 8 requires. The
  table was never optional.
- The calendar **keeps `RegisterTenantHandler` and `20-27`'s provisioner.** The account side supplies
  the id when it provisions; nothing forbids another caller supplying one. This is what keeps a
  calendar-only customer possible without making it a feature today — see Out of scope.

Deleting the table and the minting path would save one table with zero rows, and would weld shut the
only door worth keeping open. So it is explicitly not done.

## Why it is cheap

`TenantId` is `readonly record struct TenantId(Guid)`. It appears in 123 of `ago-calendar`'s 313
source files, and **none of them change** — a strongly-typed wrapper does not care where its value
came from. What changes is provenance, in one place.

The database is empty: eleven migrations, zero rows. There is no data migration and no customer to
disturb, and that is true only until the first tenant exists.

## Done when

- [x] A calendar tenant's id is the account id, end to end, proven by provisioning one and reading
      both rows. — the provisioner takes `AGO_CALENDAR_TENANT_ID` and the row reads back as that
      exact value, asserted against the database rather than the handler's return.
- [x] `RegisterTenantHandler` and the `20-27` provisioner still work for a standalone tenant. — and
      asserted **directly** by its own test rather than inferred from other tests happening not to
      break, which is what stops a later reader deleting the path as dead code.
- [x] Nothing in the calendar mints a tenancy identifier of its own any more. — with one deliberate
      exception the item asked for: the handler still mints when no id is supplied, because that is
      the door `adr/0093` keeps open.

## Outcome

Merged as `ago-calendar#29`.

**The change is one line**: `command.TenantId ?? new TenantId(idGenerator.NewId(now))`. Five files,
none of them among the 123 that pass `TenantId` around — a `record struct` does not care where its
value came from, so only provenance moved. Had it touched many of those files, it would have been a
wrong turn.

**No EF migration, and the reason was checked rather than assumed**: `tenants.id` is already
`ValueGeneratedNever()`, so the column never depended on the *application* minting the value — only on
some caller supplying one before insert. Worth stating plainly on a day when `ago-chat` took two
migrations in one wave and one had to be regenerated by hand.

**A duplicate id is refused by the primary key**, the same mechanism that already caught a repeated
public key — so no new logic, only an operator-facing message that stops claiming *which* column
collided, because it can now be wrong about that. A small correctness detail that would have been
easy to leave wrong.

### The gap this leaves, named rather than papered over

**The calendar cannot tell a genuine account id from any other GUID.** Verifying one would mean
calling the account side inside the transaction, which rule 8 forbids, or trusting an unverified
claim. Accepting an id is not the same as trusting one — and the channel that makes it trustworthy is
`22-04`'s, where the site is proved by `adr/0094`'s assertion rather than asserted.

## Out of scope

- **Selling the calendar without the chat.** The door stays open here; the product does not exist
  until somebody wants it, and the expensive half of it is not tenancy but exposure — the embeddable
  booking widget, closed by `PublicBookingApiGate` (`adr/0090`). Its own item, its own ADR revisit.
